# Multi-Agent Customer Support on Amazon Bedrock AgentCore

A five-agent support system for a demo e-commerce store ("NovaMart"). An orchestrator routes each request to
specialist agents; the policy agent retrieves from **three Bedrock Knowledge Bases in parallel**; refunds and
order lookups hit DynamoDB tools; everything runs on AgentCore Runtime behind Guardrails, with shared
workflow state and X-Ray traces for every hop.

![Architecture overview](diagrams/architecture-overview.png)

## What it does

| Agent | Model | Tools | Backing store |
|---|---|---|---|
| `OrchestratorAgent` | Claude Haiku 4.5 | `route_to_inventory_agent`, `route_to_policy_agent`, `route_to_refund_agent`, `route_to_communication_agent` | DynamoDB workflow state |
| `InventoryAgent` | Nova 2 Lite | `check_order_status`, `get_customer_tier`, `list_customer_orders` | DynamoDB orders / customers |
| `PolicyAgent` | Nova 2 Lite | `retrieve_returns_policy`, `retrieve_shipping_policy`, `retrieve_warranty_policy`, `search_all_policies` | 3 Bedrock Knowledge Bases |
| `RefundAgent` | Nova 2 Lite | `initiate_refund`, `get_inventory_context` | DynamoDB |
| `CommunicationAgent` | Nova 2 Lite | `get_full_workflow_context` | synthesizes the customer reply |

### Parallel multi-agent RAG

`search_all_policies` fans the same query out to all three knowledge bases concurrently with a
`ThreadPoolExecutor`, then merges the passages per domain before the policy agent answers. One customer
question, three retrieval calls, no serialised latency.

### Shared workflow state

Refunds need order context that a different agent fetched. A `WorkflowState` record in DynamoDB is created per
session, read before each dispatch, and patched after each tool call — so the agents cooperate without
re-querying or leaking state between sessions.

### Guardrails, memory, observability

- Bedrock Guardrails on the runtime path for policy-violating requests.
- AgentCore Memory for session persistence across invocations.
- CloudWatch structured logs + X-Ray service map, printed per scenario by the demo runner.

## How to run

```bash
pip install -r requirements.txt
cp .env.example .env              # fill in the KB IDs and project name
python config.py                  # prints resolved resource names
python infrastructure/seed_data.py   # mock customers CUST-001..004 + orders + policy docs in S3
python src/demo.py                # scripted end-to-end scenarios, one X-Ray trace id each
python tests/test_agent.py        # task checks
```

Provisioning needs `us-east-1` with: DynamoDB tables, an S3 policy bucket, an S3 Vectors index, three Bedrock
Knowledge Bases (`amazon.titan-embed-text-v2:0`), an AgentCore runtime deployed via the `agentcore` CLI
(definition in `agentcore/agentcore.json`, CDK app in `agentcore/cdk/`), and a CloudWatch log group.
Credentials resolve through the default AWS chain — never hard-code them.

```bash
agentcore validate
agentcore deploy -y
```

## What I built vs. what the scaffold provided

This is the capstone of the **AWS Agentic AI Nanodegree**. The course scaffold provided the foundation
CloudFormation stack, the AgentCore CLI wrapper (`src/agentcore_cli.py`), the KB retrieval helper, the
tracing/logging layer, the demo runner, and the task-check harness.

**Everything in `src/agent_orchestrator.py` is mine** — the agent graph, the routing tools, the parallel
three-KB retrieval design, the DynamoDB workflow-state schema, the refund state machine, the guardrail and
memory wiring, and the prompts each agent runs on (~1,900 lines).

## Data & cost notes

Store data is fictional and generated by `infrastructure/seed_data.py`; no customer records exist here. The
optional Lambda gateway step is left unimplemented — the agents use in-process tools. Running the full demo
suite against Bedrock typically costs well under a dollar in the Virginia region.
